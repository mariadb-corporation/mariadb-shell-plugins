# msm_plugin — Project Context

## Project

`msm_plugin` ("MariaDB Schema Management Plugin", MSM) is a MariaDB Shell plugin that manages one database schema across its lifecycle as a **schema project on disk**: develop the full current schema in `development/<schema>_next.sql`, snapshot it as a released version, hand-write the release-to-release update script, generate a self-contained create-or-upgrade **deployment script**, and deploy it to a server. Registers the `msm` global (plus `msm.get` / `msm.set` sub-objects). Forked from Oracle's MySQL Shell plugin; dual copyright (Oracle line kept, `Copyright (c) 2026, MariaDB plc.` added). Version `26.11.0` (`lib/general.py`, since #79 on 2026-11-03), reports itself as `PREVIEW` in `msm.info()`. Bundled into the MariaDB Shell release packages by `mariadb-shell/.github/workflows/shell-release.yml` (with `mcp_plugin` and `rest_plugin`); consumed by `mcp_plugin`'s `msm.*` MCP tools (23 tools: 12 wrapping `management.py`, 7 wrapping `modeling.py`, 4 on `lib/projects.py`) and by the ai-plugins skills in `ai-plugins/additional-skills/schema-management/` (5 skills: overview, create, develop, release, deploy).

## Architecture / key decisions

- **Two layers.** `management.py` / `general.py` / `modeling.py` are the `@plugin_function` wrappers (prompting, printing, defaults); `lib/management.py` does the work, `lib/core.py` has helpers (SQL exec, prompt, config file, update log, lock). `mcp_plugin` calls the WRAPPERS (`msm_plugin/management.py`, `msm_plugin/modeling.py`), except `lib/projects.py` and `lib/source.py`, which it imports directly.
- **Interactive vs. returning.** Every wrapper checks `lib.core.get_interactive_default()` = `shell.options.useWizards` AND main thread. Interactive: prompts for missing args and PRINTS results (returns None). Non-interactive: returns values, raises instead of printing. The CLI (`mariadb-shell -- msm ...`) runs interactive even without a TTY (prompts read stdin; `< /dev/null` takes the defaults). Tests and the MCP server set `useWizards=False`.
- **Working directory.** `msm.cd/pwd/ls` keep a plugin-own working dir in `plugin_data/msm_plugin/config.json` (`workingDirectory`, default `~`); every `schema_project_path` kwarg defaults to it. `ConfigFile` is a singleton.
- **Section model.** Scripts are split by banners `-- ####...\n-- MSM Section NNN: Title\n...-- ####` (`MSM_SECTIONS_REGEX`); text before the first banner is pseudo-section `license`. Sections are edited by id with `msm.set.sectionSqlContent` / read with `msm.get.sqlContentFromSection`; `write_sections_to_file` rejoins them with `\n`.
- **Project layout** (`templates/msm.project/` copied, `*.md` placeholders substituted, copyright block replaced): `msm.project.json`, `README.md`, `CHANGELOG.md`, `development/<file>_next.sql`, `releases/{versions,updates,deployment}/` (each with a README). `<file>` = schema name with whitespace→`_` and `\/:*?"<>|` removed (`schemaFileName`). Folder name `<file>.msm.project`.
- **Version storage.** The development version lives ONLY in section 910's `CREATE OR REPLACE ... VIEW msm_schema_version (major,minor,patch) AS SELECT x, y, z` (regex `MSM_SCHEMA_VERSION_VIEW_VALUES`); new projects start at `0.0.1`. Released versions are derived from file names in `releases/versions/` (`.*(\d+)\.(\d+)\.(\d+)\.sql`), deployable ones from `releases/deployment/`. Deployed version = the view on the server; `0.0.0` while a create/update runs.
- **prepare_release** (`lib/management.py`): requires version ≥ last released and next_version > version (or ≥ with `allow_to_stay_on_same_version`); inlines `SOURCE '<path>'[a:b];` lines (`substitute_source_statements_with_content`, now a thin wrapper of `lib/source.py`'s `expand_source_directives` - see Files that matter; one level, relative to `development/`, indentation applied; the slice is optional = whole file, each bound empty, a character offset with Python slice semantics, or `lnN` = 1-based line, end line included, `ln-1` the last; `get_source_slice`) into the dev script; fills template `schema_a.b.c.sql` section-by-section from the dev script (only section ids present in the TEMPLATE survive; section 910 is never taken from the dev script, the template's states the released version - content added to the dev file's 910 is not released), drops empty sections except `license`/`001`; writes `versions/<file>_<v>.sql`; if a previous release exists and differs, writes the EMPTY update script `updates/<file>_<prev>_to_<v>.sql` from `schema_x.y.z_to_a.b.c.sql`; then sets section 910 of the dev file to next_version.
- **generate_deployment_script**: first release → plain copy of the version file. Later releases → `schema_deployment_a.b.c.sql` with target sections 130/140/150/160/170/190 and, per consecutive released pair (`MSM-LOOP-START/END:UPDATABLE-VERSIONS` blocks, `(indent=N)`), the update script's sections 230/240/270/290. Target 160 (diagrams) is emitted after 150 and target 180 (REST) after 370, both run in full every time. Section 140 → body of `msm_create_<target>()`, each 240 → `msm_update_<from>_to_<to>()`, 170 → `msm_auth_<target>()`, 270 → `msm_auth_<from>_to_<to>()`; dispatcher `msm_create_or_update()` / `msm_auth()` pick fresh-create vs. chained updates (via `@msm_schema_init`, `@msm_current_version`); all `msm_*` procs dropped at the end. SIGNAL errnos 32100 (exists, unmanaged), 32101 (stuck at 0.0.0), 32102 (version not updatable). Requires an update file for EVERY consecutive released pair (`get_updatable_versions` raises otherwise).
- **Authorization model (verified 2026-10-05):** `msm_auth` runs the 270 step procedures, then ALWAYS the target's 170 (fresh install: only 170). So 170 must be re-runnable (`CREATE ROLE IF NOT EXISTS`, `GRANT`) and new roles/grants reach upgraded schemas through it; 270 is only for `REVOKE`/`DROP ROLE`. Upgrade and fresh install then end with identical roles and grants. The ai-plugins skills say to `GRANT` in 270 — wrong, and dangerous with issue 14.
- **deploy_schema** (`lib/management.py`): checks released == deployment-script versions, picks latest if no version; refuses an existing unmanaged schema; no-op message if already on version; message (not error) if server is NEWER than the project; refuses a version not in the update chain. Takes the per-schema update lock (`lib.core.msm_update_lock`, `GET_LOCK(CONCAT("MSM_METADATA_LOCK", "_", MD5(schema)), 1)`) before it looks at the schema and holds it through the backup, the script and the drop/restore; runs the script via `lib.core.execute_msm_sql_script(take_lock=False)` (`mysqlsh.mysql.split_script`, so `DELIMITER` works). `backup=True` (default False, added in a MariaDB session) + existing schema: sets `GLOBAL local_infile=1` if needed, `util.dump_schemas` (through `lib.core.run_util`: the given session becomes the global one only for the call, under the `_mariadb_shell_plugins_global_session` lock the rest_plugin shares) to `backup_directory` (default `plugin_data/msm_plugin/backups/<file>_backup_<ver>[_N]`), on failure DROP + `util.load_dump`, removes the dump either way. Without backup a failed UPDATE leaves the schema as the failure left it; a failed fresh CREATE drops the schema. Every step goes to `plugin_data/msm_plugin/msm_schema_update_log.txt`.
- **Project list (PR #80).** The schema projects the user works with, so a client (the VS Code extension's MSM Projects view, over mcp_plugin's `msm.list_projects` etc.) can show them without searching the disk. `lib/projects.py` keeps `plugin_data/msm_plugin/projects.json` (the shell user's list) and `projects/<owner>.json` (one per MCP user in multi-tenant mode, `owner` = the `mcp_user_id` UUID, validated before it becomes a file name; `remove_owner` when the user goes): `{"version": 1, "projects": {"<abs project path>": {"folder", "caption", "color"}}}`, each detail written only when set. The rules copy mcp_plugin's connection details (same `folder` normalization, 100-char one-line caption, the same six `COLORS` - an mcp test pins the parity), so the extension shows both lists with one piece of code; the list folder is called `folder`, not `path`, because `project_path` is the file system path. The file IS the record (unlike `connections.json`), so every change takes an advisory `<file>.lock` (`_file_lock`, flock / msvcrt) and writes `.tmp` + `os.replace`; a listing reads leniently (a damaged file lists nothing), a change reads strictly (never overwrites a damaged file). `list_projects` adds `schema_name` (from `msm.project.json`, None if unreadable) and `exists` per entry; a moved/deleted project stays listed so a client can show it missing and remove it. Module-level imports are shell-free (`get_data_path` imports `lib.core` lazily), so mcp_plugin imports it directly like `lib/source.py`. Shell functions: `msm.listProjects`, `msm.addProject(project_path, folder=, caption=, color=)` (re-adding updates the details given), `msm.updateProject` (None keeps, `""` clears), `msm.removeProject` (list only). `msm.createNewProjectFolder` adds the new project unless `add_to_project_list=False` (what the MCP wrapper passes, adding to the caller's own list instead). Each entry also stores `mcpAccess` (always written; missing reads as True): `add_project(..., mcp_access=None, default_mcp_access=True)` (None keeps a listed project's, a new one gets the default - mcp_plugin passes False from a `--gui` server), `update_project(..., mcp_access=)`, `list_projects(owner, mcp_access_only=)`, and `find_restricted_project(path, owner)` (the listed project with no access that holds a path, links resolved, `""` taken as the working directory as the tools take it, and case folded (with NFC) where the volume ignores it: `_ignores_case` asks the disk, since `os.path.normcase` folds on Windows only and macOS ignores case too; `_stored_key` folds the same way, so a re-cased add changes the listed entry) for mcp_plugin's `require_project_access`. The shell functions take `mcp_access` as a keyword argument, default True.
- **Schema diagrams (Section 160).** The VIEW `msm_schema_diagrams (name, format, document)`, written by msm only: row `schema_definition` in `msm-schema/1` = the lsp-server outline's own shape (tables/views/routines/triggers/events/sequences of the project's schema, `range`/`selection_range` as the outline writes them, 0-based lines + UTF-16 characters, `source` n = `files[n + 1]`), plus per FK `many` (no PK/UNIQUE covering exactly its columns), `referenced_mandatory` (all FK columns NOT NULL) and `mandatory` (always True) - MySQL Workbench's meanings, checked against a Workbench model's data. `source_hash` = sha256 of the development script with Section 160 REMOVED, banner and joining line break included (not blanked: the hash must not change when only diagrams do, nor when msm adds the section to an older script), SOURCE expanded. One `msm-diagram/1` row per diagram (layers/figures/connections, camelCase keys as Workbench's). The CREATE statements are the source of truth; the snapshot is only ever made from them.
  - `lib/diagrams.py` = the format only, no shell imports: render/parse the VIEW (string literals with backslash escapes, read with one regex `_TOKENS`), `dump_document` (a value on one line when <= 160 chars, children rendered first so every value is written once - both matter at MB-sized VIEWs), `schema_document_from_outline`, `unread_statements`, `validate_diagram`, `reconcile_diagram` (drops figures/connections of tables and FKs the snapshot no longer has, never adds).
  - `lib/lsp.py` = finding (`find_lsp`: given path, next to the shell via `mysqlsh.executable`, PATH, `~/.local/bin`; a candidate counts only if `--version` answers `mariadb-lsp ...`) and running `mariadb-lsp outline` (stdin + `--source-dir development`; the binary expands SOURCE itself, so positions are per file).
  - `lib/modeling.py` = the section in a project. Inline while the VIEW fits `maxInlineSectionSize` (optional in msm.project.json, default 16384; a large value keeps a single-file script), else `development/sections/160_schema_diagrams.sql` with the project's notices as header and `[lnN:]`; once included it stays included (the file's part outside the slice kept), and a slice that would not hold the whole rewritten VIEW is refused. The outline gets Section 160 BLANKED (lines kept, so positions match the file). Every operation reads the project once (`_Project.load`: settings, script, sections; `_Project.read` reads each SOURCE file once); only files whose text changes are written. A dev script without 160 gets it inserted after 150 from the template.
  - Includes are checked through `source.checked_includes(check)` (a contextvar consulted by `source.read_include` and `checked_include_path`; `check(path)` returns the path to use or raises), not a parameter: mcp sets it once per tool call, which also covers `prepare_release`'s own expansion.
  - Shell functions (`modeling.py`): `msm.listSchemaDiagrams` (with `current` = snapshot hash matches the script), `getSchemaDiagrams`, `updateSchemaDefinition`, `setSchemaDiagram` (`document`, or `document_file` = a JSON file, for the CLI), `removeSchemaDiagram`, `createSchemaDiagram`, `layoutSchemaDiagram` (`--tables` as JSON on the CLI).
  - **Unnamed foreign keys** get MariaDB's own name in the snapshot (`_name_foreign_keys`): `<table>_ibfk_<n>`, n one more than the highest so far, skipping names the SQL gives (ha_innodb.cc `dict_table_get_foreign_id` / `dict_create_add_foreign_id`), marked `generated_name: true`. A FK with only an index name (`FOREIGN KEY idx (...)`) is named after it by the server (sql_yacc.yy: constraint name = CONSTRAINT symbol, else the index ident), and the outline already does so. So every connection has a `foreignKey` to point at.
  - **Layout** (`lib/layout.py`, pure Python): layered Sugiyama. FK edges child -> parent (parent on top); connected components laid out separately (largest first, wrapped at ~1.5 x sqrt(total area)), FK-less tables packed in rows below; cycles broken by reversing DFS back edges, self references left out; longest-path layers, then each parent moved down to just above its highest child; dummy nodes on long edges; 4 down/up barycenter sweeps keeping the fewest crossings; x by least squares towards the neighbours' mean under the order and gap constraints (pool adjacent violators), GAP 80 (Workbench), 40 next to a dummy; rows = tallest figure + 80. Deterministic; a final overlap check raises. 400 tables in well under a second. Figure size from tableCard.ts's metrics (`figure_width`: longest `name type` row or the title, 6.2 / 8.4 px per char, rounded up to 10, 120..360; `figure_height`: the card's own sums, honouring `expanded` / `columnsExpanded` / `indicesExpanded` / `foreignKeysExpanded`).
  - `lib/modeling.py`: `create_diagram(path, name, tables=None)` (all tables by default) and `layout_diagram(path, name, tables=None, keep_placed=True)` (tables = ones to ADD). Both first take the snapshot as is if its `source_hash` matches the script, else make it again (`_current_snapshot`, which reconciles diagrams like updateSchemaDefinition); both add a connection for every FK between two shown tables that has none (same-schema references only). A figure is "placed" when it has numeric `left` and `top`, so a document given to setSchemaDiagram may leave them out and layoutSchemaDiagram places it. Figures on a layer always stay (their positions are layer-relative); with `keep_placed` so do all placed ones, and the moved ones go as one block below everything that stays (layers included), else at MARGIN 40. Diagram width/height grow to cover the figures + 40. New figures: uuid4 ids, `#98BFDA`, `expanded: true`, `manualSizing: false`, estimated width and height; a moved figure keeps its width unless it has none, and gets its height recomputed unless `manualSizing`.
  - The remaining parts (Workbench import, section splitting, edits through the language server): Next steps 10.
- **A release needs a matching snapshot**: `prepare_release` refuses an existing version file first, then calls `modeling.update_schema_definition`, which fails without the binary or on any outline note with `applied: false` (every note has `kind` + `applied`, see lsp-server docs/outline-format.md "Notes": syntax-error, unsupported-sql-mode, unknown-table for ALTER TABLE / CREATE INDEX, include-unreadable, include-nested; an unknown kind also goes by `applied`; a binary without `applied` falls back to "not read" in the message). The snapshot rewrites the development files (Section 160, pruned diagrams) before the release's later checks, like section 910 they are not in the returned file list. Every release and deployment therefore creates the `msm_schema_diagrams` VIEW, top level in the deployment script (`${section_160_schema_diagrams}` after 150), no update-script counterpart.
- **Copyrights.** `msm.project.json` has a `copyrights` list (`holder`, `yearOfCreation`, `yearOfLastUpdate`, `tracksUpdates`) plus the legacy `copyrightHolder` mirror; old projects are migrated on read (`get_project_copyrights`). Licenses = `templates/license/*.txt` (`BSD`, `GPL-2.0`, `MIT`, `None`) or `CUSTOM` with `customLicense` text; placeholders `${copyright_notices}`, `${copyright_holder}`, `${year}`. Template files' own copyright headers are stripped (`strip_template_copyright_header`).

## Files that matter

- `init.py` -> registers `msm`, `msm.get`, `msm.set`
- `management.py` -> the `@plugin_function` wrappers for project, release, deployment, server checks (what the CLI, Python and `mcp_plugin` call)
- `general.py` -> `msm.info/version/pwd/cd/ls`
- `lib/source.py` -> the ONE implementation of MSM SOURCE (regex, slices, `resolve_include_path`, `expand_source_directives` with segments, `locate`, `directives`, `directive_slices`, the include check `checked_includes` / `checked_include_path`); no shell imports, so mcp_plugin's `db.execute_sql_script` and `sql.*` tools import it too (PRs #60, #61, #63, 2026-10-19). Keep it in step with the language server's rules (lsp-server docs/plans/source-includes.md).
- `lib/projects.py` -> the project list (see Architecture): normalizers, `list_projects` / `add_project` / `update_project` / `remove_project` / `remove_owner`, all taking `owner=`
- `lib/diagrams.py`, `lib/layout.py`, `lib/lsp.py`, `lib/modeling.py`, `modeling.py` -> the schema diagrams (see Architecture); `tests/unit/test_diagrams.py`, `tests/unit/test_layout.py` (imports the `project` fixture and helpers from test_diagrams; pure layout tests need nothing, the modeling ones run the real binary)
- `lib/management.py` -> sections, project creation, copyrights/licenses, `prepare_release`, `generate_deployment_script`, `deploy_schema`
- `lib/core.py` -> `ConfigFile`, working dir, interactive check, `MsmDbExec`, update log, `execute_msm_sql_script` (lock + split_script)
- `templates/scripts/schema_next.sql`, `schema_a.b.c.sql`, `schema_x.y.z_to_a.b.c.sql`, `schema_deployment_a.b.c.sql` -> the section layouts; the deployment template's placeholders decide which sections ever reach a server
- `templates/msm.project/` -> scaffolded project files; `templates/license/` -> license headers
- `tests/conftest.py`, `tests/unit/test_management.py` -> sandbox fixture; release/deploy/backup tests; `tests/unit/test_projects.py` -> the project list, on a monkeypatched `projects.get_data_path`
- `run_tests.py` -> symlinks the plugin into a temp `dot_mariadb_shell`, pip-installs `requirements.txt`, runs pytest in the shell
- `../mcp_plugin/lib/msm_functions.py` -> the MCP wrappers (path guard, `msm.deploy_schema` only with the `db` group; the diagram tools and `msm.prepare_release` run through `_in_project`: authorize, then the msm call in a worker thread inside `source.checked_includes`)
- `~/git/ai-plugins/additional-skills/schema-management/*/SKILL.md` -> agent-facing docs of the workflow (section rules, SOURCE syntax)

## Gotchas / things not to repeat

- **A test sandbox can outlive its run**: if a suite's setup fails, the sandbox on 3388 keeps running after its temp dir is deleted, so `sandbox kill` cannot find it and the next run (msm or mrs) fails with `Port '3388' is already in use`. Check `ps` that the `--defaults-file` is under the pytest temp dir, then kill the pid.
- **Run the suite from the plugin dir** as `mariadb-shell --py -f run_tests.py` with `/opt/homebrew/bin` on PATH (`mariadbd`) and `MARIADB_SHELL` pointing at a shell that has `util.dump_schemas` (builds from 2026-10-01 on; `~/.local/bin/mariadb-shell` from Sep 29 lacks it). Never `pip install msm` — that is an unrelated PyPI package.
- **`MARIADB_SHELL_USER_CONFIG_HOME` moves `plugin_data/msm_plugin`** (config, log, backups) — use a scratch one for experiments so the user's `workingDirectory` and update log are untouched.
- **Interactive mode changes return values**: wrappers print and return None when `useWizards` is on. Set `shell.options.useWizards = False` in scripts that need the values.
- **The `msm.set.sectionSqlContent` arguments are positional `file_path, section_id, sql_content`**; sections 140/170 (dev) and 240/270 (update) end up inside stored procedures — no `DELIMITER` there; 130/150/190/230/290 are top level and use `DELIMITER %%`.
- **Scripting the release functions** (used 2026-10-08 for the MRS metadata 5.0.0): from
  `mariadb-shell --py -f`, with a config home whose `plugins/msm_plugin` links to this repo
  (otherwise `ModuleNotFoundError: msm_plugin`), `useWizards` False, then
  `lib.management.set_development_version`, `prepare_release(version, next_version)`,
  `set_section_sql_content(section_id, sql_content, file_path)` on the update script and
  `generate_deployment_script(..., overwrite_existing=True)` to regenerate after an edit.
- **Section 240 runs INSIDE a stored procedure** (`msm_update_<from>_to_<to>`): a
  `DROP FUNCTION`/`PROCEDURE` there fails with MariaDB 1357 ("Can't drop or alter a
  FUNCTION from within another stored routine"); put such drops in 290. MariaDB also
  refuses to alter a column that is part of a FOREIGN KEY (1833): drop the FKs, alter,
  re-add them, all in 240.
- **The shell exposes plugin functions in snake_case in Python mode** (`msm.list_projects()`, `msm.add_project(...)`), camelCase is the registered FQN; the CLI form is `mariadb-shell -- msm list-projects` / `add-project <path> --folder=/Shop --color=green`. Verified 2026-11-04 through a scratch config home with `plugins/msm_plugin` linked to the repo.
- **CI runs on a case-sensitive Linux disk, the Mac on a case-insensitive one**: a test about case folding must branch on what the disk says (`os.path.exists` of the re-cased path) for every step, or it passes locally and fails in CI (an `add_project` of a re-cased path that does not exist there).
- **What a plugin function receives (checked with a probe plugin in a scratch config home):** from Python mode the shell's own `Dict` / `List` at every level, but they subclass `dict` / `list`, so `isinstance` and `json.dumps` work. This shell has no JavaScript mode. On the CLI a positional JSON object for a `dict` parameter is refused ("The following argument is invalid"); named options go into the dict parameter (documented keyword options go to `**kwargs`), each value parsed as JSON when it can be - also for a `str` option, which then fails with "String expected, but value is Map". Option names are camelCased, even `--x_y` -> `xY`. So a whole document comes in as a file (`msm set-schema-diagram --document-file=d.json`).
- **msm finds `mariadb-lsp` next to the running shell before the PATH**: a stale copy in a shell build folder wins over a newer standalone lsp-server build on the PATH. To test with another binary, move the shell's copy aside for the run (and back), or pass `lsp_path`.
- **A docstring line ending in `:` is a section header to the shell's plugin parser**: "Invalid format: section without content", and the whole `msm` object fails to register (every msm test then dies with `No module named 'msm_plugin'`).
- **Legal notices are additive**: keep Oracle's line and the FOSS exception, add exactly `Copyright (c) 2026, MariaDB plc.`.
