# msm_plugin — Project Context

## Project

`msm_plugin` ("MariaDB Schema Management Plugin", MSM) is a MariaDB Shell plugin that manages one database schema across its lifecycle as a **schema project on disk**: develop the full current schema in `development/<schema>_next.sql`, snapshot it as a released version, hand-write the release-to-release update script, generate a self-contained create-or-upgrade **deployment script**, and deploy it to a server. Registers the `msm` global (plus `msm.get` / `msm.set` sub-objects). Forked from Oracle's MySQL Shell plugin; dual copyright (Oracle line kept, `Copyright (c) 2026, MariaDB plc.` added). Version `26.11.0` (`lib/general.py`, since #79 on 2026-11-03), reports itself as `PREVIEW` in `msm.info()`. Bundled into the MariaDB Shell release packages by `mariadb-shell/.github/workflows/shell-release.yml` (with `mcp_plugin` and `rest_plugin`); consumed by `mcp_plugin`'s `msm.*` MCP tools (25 tools: 13 wrapping `management.py`, 8 wrapping `modeling.py`, 4 on `lib/projects.py`) and by the ai-plugins skills in `ai-plugins/additional-skills/schema-management/` (5 skills: overview, create, develop, release, deploy).

## Architecture / key decisions

- **Two layers.** `management.py` / `general.py` / `modeling.py` are the `@plugin_function` wrappers (prompting, printing, defaults); `lib/management.py` does the work, `lib/core.py` has helpers (SQL exec, prompt, config file, update log, lock). `mcp_plugin` calls the WRAPPERS (`msm_plugin/management.py`, `msm_plugin/modeling.py`), except `lib/projects.py` and `lib/source.py`, which it imports directly.
- **Interactive vs. returning.** Every wrapper checks `lib.core.get_interactive_default()` = `shell.options.useWizards` AND main thread. Interactive: prompts for missing args and PRINTS results (returns None). Non-interactive: returns values, raises instead of printing. The CLI (`mariadb-shell -- msm ...`) runs interactive even without a TTY (prompts read stdin; `< /dev/null` takes the defaults). Tests and the MCP server set `useWizards=False`.
- **Working directory.** `msm.cd/pwd/ls` keep a plugin-own working dir in `plugin_data/msm_plugin/config.json` (`workingDirectory`, default `~`); every `schema_project_path` kwarg defaults to it. `ConfigFile` is a singleton.
- **Section model.** Scripts are split by banners `-- ####...\n-- MSM Section NNN: Title\n...-- ####` (`MSM_SECTIONS_REGEX`); text before the first banner is pseudo-section `license`. Sections are edited by id with `msm.set.sectionSqlContent` / read with `msm.get.sqlContentFromSection`; `write_sections_to_file` rejoins them with `\n`.
- **Project layout** (`templates/msm.project/` copied, `*.md` placeholders substituted, copyright block replaced): `msm.project.json`, `README.md`, `CHANGELOG.md`, `development/<file>_next.sql`, `releases/{versions,updates,deployment}/` (each with a README). `<file>` = schema name with whitespace→`_` and `\/:*?"<>|` removed (`schemaFileName`). Folder name `<file>.msm.project`.
- **Version storage.** The development version lives ONLY in section 910's `CREATE OR REPLACE ... VIEW msm_schema_version (major,minor,patch) AS SELECT x, y, z` (regex `MSM_SCHEMA_VERSION_VIEW_VALUES`); new projects start at `0.0.1`. Released versions are derived from file names in `releases/versions/` (`.*(\d+)\.(\d+)\.(\d+)\.sql`), deployable ones from `releases/deployment/`. Deployed version = the view on the server; `0.0.0` while a create/update runs.
- **prepare_release** (`lib/management.py`): requires version ≥ last released and next_version > version (or ≥ with `allow_to_stay_on_same_version`); inlines `SOURCE '<path>'[a:b];` lines (`substitute_source_statements_with_content`, now a thin wrapper of `lib/source.py`'s `expand_source_directives` - see Files that matter; one level, relative to `development/`, indentation applied; the slice is optional = whole file, each bound empty, a character offset with Python slice semantics, or `lnN` = 1-based line, end line included, `ln-1` the last; `get_source_slice`) into the dev script; fills template `schema_a.b.c.sql` section-by-section from the dev script (only section ids present in the TEMPLATE survive; section 910 is never taken from the dev script, the template's states the released version - content added to the dev file's 910 is not released), drops empty sections except `license`/`001`; writes `versions/<file>_<v>.sql`; if a previous release exists and differs, writes the EMPTY update script `updates/<file>_<prev>_to_<v>.sql` from `schema_x.y.z_to_a.b.c.sql`; then sets section 910 of the dev file to next_version.
- **generate_deployment_script**: first release → plain copy of the version file. Later releases → `schema_deployment_a.b.c.sql` with target sections 130/140/150/160/170/190 and, per consecutive released pair (`MSM-LOOP-START/END:UPDATABLE-VERSIONS` blocks, `(indent=N)`), the update script's sections 230/240/270/290. Target 160 (diagrams) is emitted after 150 and target 180 (REST) after 370, both run in full every time. Section 140 → body of `msm_create_<target>()`, each 240 → `msm_update_<from>_to_<to>()`, 170 → `msm_auth_<target>()`, 270 → `msm_auth_<from>_to_<to>()`; dispatcher `msm_create_or_update()` / `msm_auth()` pick fresh-create vs. chained updates (via `@msm_schema_init`, `@msm_current_version`); all `msm_*` procs dropped at the end. SIGNAL errnos 32100 (exists, unmanaged), 32101 (stuck at 0.0.0), 32102 (version not updatable). Requires an update file for EVERY consecutive released pair (`get_updatable_versions` raises otherwise).
- **Authorization model (verified 2026-10-05):** `msm_auth` runs the 270 step procedures, then ALWAYS the target's 170 (fresh install: only 170). So 170 must be re-runnable (`CREATE ROLE IF NOT EXISTS`, `GRANT`) and new roles/grants reach upgraded schemas through it; 270 is only for `REVOKE`/`DROP ROLE`. Upgrade and fresh install then end with identical roles and grants. The ai-plugins skills say to `GRANT` in 270 — wrong, and dangerous with issue 14.
- **deploy_schema** (`lib/management.py`): checks released == deployment-script versions, picks latest if no version; refuses an existing unmanaged schema; no-op message if already on version; message (not error) if server is NEWER than the project; refuses a version not in the update chain. Takes the per-schema update lock (`lib.core.msm_update_lock`, `GET_LOCK(CONCAT("MSM_METADATA_LOCK", "_", MD5(schema)), 1)`) before it looks at the schema and holds it through the backup, the script and the drop/restore; runs the script via `lib.core.execute_msm_sql_script(take_lock=False)` (`mysqlsh.mysql.split_script`, so `DELIMITER` works). `backup=True` (default False, added in a MariaDB session) + existing schema: sets `GLOBAL local_infile=1` if needed, `util.dump_schemas` (through `lib.core.run_util`: the given session becomes the global one only for the call, under the `_mariadb_shell_plugins_global_session` lock the rest_plugin shares) to `backup_directory` (default `plugin_data/msm_plugin/backups/<file>_backup_<ver>[_N]`), on failure DROP + `util.load_dump`, removes the dump either way. Without backup a failed UPDATE leaves the schema as the failure left it; a failed fresh CREATE drops the schema. Every step goes to `plugin_data/msm_plugin/msm_schema_update_log.txt`.
- **Project list (PR #80).** The schema projects the user works with, so a client (the VS Code extension's MSM Projects view, over mcp_plugin's `msm.list_projects` etc.) can show them without searching the disk. `lib/projects.py` keeps `plugin_data/msm_plugin/projects.json` (the shell user's list) and `projects/<owner>.json` (one per MCP user in multi-tenant mode, `owner` = the `mcp_user_id` UUID, validated before it becomes a file name; `remove_owner` when the user goes): `{"version": 1, "projects": {"<abs project path>": {"folder", "caption", "color"}}}`, each detail written only when set. The rules copy mcp_plugin's connection details (same `folder` normalization, 100-char one-line caption, the same six `COLORS` - an mcp test pins the parity), so the extension shows both lists with one piece of code; the list folder is called `folder`, not `path`, because `project_path` is the file system path. The file IS the record (unlike `connections.json`), so every change takes an advisory `<file>.lock` (`_file_lock`, flock / msvcrt) and writes `.tmp` + `os.replace`; a listing reads leniently (a damaged file lists nothing), a change reads strictly (never overwrites a damaged file). `list_projects` adds `schema_name` (from `msm.project.json`, None if unreadable) and `exists` per entry; a moved/deleted project stays listed so a client can show it missing and remove it. Module-level imports are shell-free (`get_data_path` imports `lib.core` lazily), so mcp_plugin imports it directly like `lib/source.py`. Shell functions: `msm.listProjects`, `msm.addProject(project_path, folder=, caption=, color=)` (re-adding updates the details given), `msm.updateProject` (None keeps, `""` clears), `msm.removeProject` (list only). `msm.createNewProjectFolder` adds the new project unless `add_to_project_list=False` (what the MCP wrapper passes, adding to the caller's own list instead). Each entry also stores `mcpAccess` (always written; missing reads as True): `add_project(..., mcp_access=None, default_mcp_access=True)` (None keeps a listed project's, a new one gets the default - mcp_plugin passes False from a `--gui` server), `update_project(..., mcp_access=)`, `list_projects(owner, mcp_access_only=)`, and `find_restricted_project(path, owner)` (the listed project with no access that holds a path, links resolved, `""` taken as the working directory as the tools take it, and case folded (with NFC) where the volume ignores it: `_ignores_case` asks the disk, since `os.path.normcase` folds on Windows only and macOS ignores case too; `_stored_key` folds the same way, so a re-cased add changes the listed entry) for mcp_plugin's `require_project_access`. The shell functions take `mcp_access` as a keyword argument, default True.
- **Schema diagrams (Section 160).** The VIEW `msm_schema_diagrams (name, format, document)`, written by msm only: row `schema_definition` in `msm-schema/1` = the lsp-server outline's own shape (tables/views/routines/triggers/events/sequences of the project's schema, `range`/`selection_range` as the outline writes them, 0-based lines + UTF-16 characters, `source` n = `files[n + 1]`), plus per FK `many` (no PK/UNIQUE covering exactly its columns), `referenced_mandatory` (all FK columns NOT NULL) and `mandatory` (always True) - MySQL Workbench's meanings, checked against a Workbench model's data. `source_hash` = sha256 of the development script with Section 160 REMOVED, banner and joining line break included (not blanked: the hash must not change when only diagrams do, nor when msm adds the section to an older script), SOURCE expanded. One `msm-diagram/1` row per diagram (layers/figures/connections, camelCase keys as Workbench's). The CREATE statements are the source of truth; the snapshot is only ever made from them.
  - `lib/diagrams.py` = the format only, no shell imports: render/parse the VIEW (string literals with backslash escapes, read with one regex `_TOKENS`), `dump_document` (a value on one line when <= 160 chars, children rendered first so every value is written once - both matter at MB-sized VIEWs), `schema_document_from_outline`, `unread_statements`, `validate_diagram`, `reconcile_diagram` (drops figures/connections of tables and FKs the snapshot no longer has, never adds).
  - `lib/lsp.py` = finding (`find_lsp`: given path, next to the shell via `mysqlsh.executable`, PATH, `~/.local/bin`; a candidate counts only if `--version` answers `mariadb-lsp ...`) and running `mariadb-lsp outline` (stdin + `--source-dir development`; the binary expands SOURCE itself, so positions are per file) and `mariadb-lsp split --format json` (`lsp.split`: the shell's own splitter, following DELIMITER and SET sql_mode, with exact UTF-8 byte offsets `begin`/`body_end`/`end`; SOURCE not expanded; an `open_at_end` string/comment is an error).
  - `lib/modeling.py` = the section in a project. Inline while the VIEW fits `maxInlineSectionSize` (optional in msm.project.json, default 16384; a large value keeps a single-file script), else `development/sections/160_schema_diagrams.sql` with the project's notices as header and `[lnN:]`; once included it stays included (the file's part outside the slice kept), and a slice that would not hold the whole rewritten VIEW is refused. The outline gets Section 160 BLANKED (lines kept, so positions match the file). Every operation reads the project once (`_Project.load`: settings, script, sections; `_Project.read` reads each SOURCE file once); only files whose text changes are written. A dev script that lacks 160, or any other template section, gets it from the template (`sections.complete_sections`, run by `_Project.load`, so the hash, the outline and the script written agree; the file itself is completed with the next write).
  - Includes are checked through `source.checked_includes(check)` (a contextvar consulted by `source.read_include` and `checked_include_path`; `check(path)` returns the path to use or raises), not a parameter: mcp sets it once per tool call, which also covers `prepare_release`'s own expansion.
  - Shell functions (`modeling.py`): `msm.listSchemaDiagrams` (with `current` = snapshot hash matches the script), `getSchemaDiagrams`, `editSchema` (see Schema edits below), `getSchemaDiagramImage` (`diagram`, `figure_id`: the picture `elide_images` leaves out, lib `get_diagram_image`), `updateSchemaDefinition`, `setSchemaDiagram` (`document`, or `document_file` = a JSON file, for the CLI), `removeSchemaDiagram`, `createSchemaDiagram`, `layoutSchemaDiagram` (`--tables`, `--views`, `--routines`, `--events`, `--sequences` as JSON on the CLI).
  - **Unnamed foreign keys** get MariaDB's own name in the snapshot (`diagrams.name_foreign_keys`; `_current_snapshot` also runs it over a stored snapshot it reuses, so one written before the naming lays out too): `<table>_ibfk_<n>`, n one more than the highest so far, skipping names the SQL gives (ha_innodb.cc `dict_table_get_foreign_id` / `dict_create_add_foreign_id`), marked `generated_name: true`. A FK with only an index name (`FOREIGN KEY idx (...)`) is named after it by the server (sql_yacc.yy: constraint name = CONSTRAINT symbol, else the index ident), and the outline already does so. So every connection has a `foreignKey` to point at.
  - **Layout** (`lib/layout.py`, pure Python): layered Sugiyama. FK edges child -> parent (parent on top); connected components laid out separately (largest first, wrapped at ~1.5 x sqrt(total area)), FK-less tables packed in rows below; cycles broken by reversing DFS back edges, self references left out; longest-path layers, then each parent moved down to just above its highest child; dummy nodes on long edges; 4 down/up barycenter sweeps keeping the fewest crossings; x by least squares towards the neighbours' mean under the order and gap constraints (pool adjacent violators), GAP 80 (Workbench), 40 next to a dummy; rows = tallest figure + 80. Deterministic; a final overlap check raises. 400 tables in well under a second. Figure size from tableCard.ts's metrics (`figure_width`: longest `name type` row or the title, 6.2 / 8.4 px per char, rounded up to 10, 120..360; `figure_height`: the card's own sums, honouring `expanded` / `columnsExpanded` / `indicesExpanded` / `foreignKeysExpanded`).
  - **Figure types** (`lib/diagrams.py`): `TableFigure` (default, `table`), `ViewFigure` (`view`; card = name + the columns the outline lists, i.e. only declared ones - deriving the SELECT's output columns is a later lsp-server PR), `RoutineGroupFigure` (`name`, `routines: [names]`, Workbench's shape: ONE card listing several routines, rows `name(param types): returns` via `routine_label`; reconcile drops lost routines and the figure when empty), `EventGroupFigure` (`name`, `events: [names]`, colour `#F5C39A`, rows `name schedule`; the same group handling as routines, `kind.many` / `kind.key` / `figure_members`), `SequenceFigure` (`sequence`, `#C9B8E8`, rows type / `START WITH` / `INCREMENT BY`; like a view). Triggers are no figure: a table card's Triggers section (`triggersExpanded`, shown unless False; `diagrams.catalog` gives a table copy `triggers` from the snapshot's `triggers` by `table`, for `_table_sections`). Agreed with vscode-extension #30 on 2026-11-06. `NoteFigure` (`text`, `font`, `textColor`) and `ImageFigure` (`image` = data URL, `keepAspectRatio`): the last two are kept as they are and never laid out. mcp's `get_schema_diagrams` returns diagrams through `diagrams.elide_images` (`image` -> `image_size`), and lib `set_diagram` runs `diagrams.keep_images` so a figure sent without its picture keeps the stored one (same id). No connections for views/routines (as Workbench). The three object kinds are ONE registry, `FIGURE_KINDS[type] = FigureKind(key, objects, many, color, rows, sections)` (key = the figure member naming the object = Workbench's link key; objects = the `catalog()` list; rows/sections = what the card shows), so reconcile, `figure_objects`, `figure_object_name`, modeling's `_add_object_figures`/`_size_figure` and workbench's `_convert_figure` are lookups, not per-type chains; the routine group (`many`) is the one special case. Colours and `ROUTINE_GROUP_NAME` live there too. `lib/layout.py` has the one `card_size(title, rows, sections, figure)` (plus `figure_width/height` for tables) and no figure-kind knowledge. The VIEW tokeniser takes runs possessively (`[^'\\]++`, Python 3.11+), as embedded images make a literal of MBs.
  - `lib/modeling.py`: `create_diagram(path, name, tables=None, lsp_path=None, views=None, routines=None)` (all tables by default, views/routines only when named - the user's decision) and `layout_diagram(path, name, tables=None, keep_placed=True, lsp_path=None, views=None, routines=None)` (lists = what to ADD; routines join the diagram's first routine group figure, `Routines` is made where there is none, and the card grows unless `manualSizing`). Both first take the snapshot as is if its `source_hash` matches the script, else make it again (`_current_snapshot`, which reconciles diagrams like updateSchemaDefinition); both add a connection for every FK between two shown tables that has none (same-schema references only). A figure is "placed" when it has numeric `left` and `top`, so a document given to setSchemaDiagram may leave them out and layoutSchemaDiagram places it. Figures on a layer always stay (their positions are layer-relative); with `keep_placed` so do all placed ones, and the moved ones go as one block below everything that stays (layers included), else at MARGIN 40. Diagram width/height grow to cover the figures + 40. New figures: uuid4 ids, `#98BFDA`, `expanded: true`, `manualSizing: false`, estimated width and height; a moved figure keeps its width unless it has none, and gets its height recomputed unless `manualSizing`.
  - **MySQL Workbench import** (`msm.importWorkbenchModel(model_path, target_path)`, mcp `msm.import_workbench_model`; NEW projects only, by the user's decision). `lib/workbench.py` (no shell imports): `read_model` unzips the .mwb, parses `document.mwb.xml` GRT XML into dicts (`_struct`, `_id`, members by `key`; `<link>` = `_Link` id, followed with `model.objects.get`, which tries the id with and without braces), reads `@db/data.db` (SQLite; a table per model table named by its id, columns named by column ids, first column `_`; a table of a deleted model table is stale and skipped with a warning) and lists the attached scripts (reported as `scripts_not_imported`, never imported) and reads `@images/`. `schema_sql` writes MariaDB SQL: tables topologically (a FK closing a cycle goes into 140-20 as ALTER TABLE ADD CONSTRAINT), types as Workbench's forward engineering (simple type from the link id `com.mysql.rdbms.mysql.datatype.<x>`, `_f` = fractional, fsp in `length`; explicit params for ENUM/SET; flags), a user type replaced by its `sqlDefinition` (MRS: UUID), `IGNORED` for invisible indexes, PK without ASC; INSERTs (`\func ` prefix = expression, numbers unquoted for numeric types); views/routines/triggers/events classified by their CREATE statement (`statement_kind`, in `lib/statements.py`: the MRS model's only "routine" is a CREATE EVENT with a SYNTAX_ERROR name), made idempotent (CREATE OR REPLACE for VIEW/EVENT, DROP ... IF EXISTS first otherwise), each kind its own `DELIMITER %%` block; roles with `GRANT ... ON *` (the script runs after USE, so it follows schema-name substitutions) or on the linked object. `diagram_documents`: table, view, routine group (the group's routines that the schema has), note and image figures (`_convert_figure`; the picture read from `@images/` of the still-open archive (`Model.images` = sizes, `Model.path`) and embedded as a data URL; one over `MAX_IMAGE_SIZE` 512 KB, past the diagram's `MAX_DIAGRAM_IMAGES_SIZE` 4 MB in all, or missing from the archive is a warning), other schemas' objects and other kinds counted in a warning; positions relative to their layer as Workbench has them, root layer dropped, connections by FK name with `table` = the FK's owner. GRT writes an object in full at its first occurrence and as a `<link>` everywhere else, keys alphabetical, so a routine in a routine group is a link in the schema's `routines`: `read_model` follows every list's links once (`_follow_list_links`). Scripts are under `@scripts/` or `@sqlscripts/` (sakila_full); a statement's leading comments (`-- View structure for view`) are skipped by `_strip_statement`.
  - `lib/sections.py`: the general section writer: `write_section_parts(project, section_id, [Part(file_name, title, sql)])` replaces a section's body, inline while the joined parts fit `maxInlineSectionSize` (`get_max_inline_section_size` lives here now), else every part into `development/sections/<file_name>` with the notices header and a `SOURCE './sections/<f>'[lnN:]; -- Without the header` each. Files and their order: `SECTION_PARTS` (`PartLayout(file_name, title, kinds)`), shared by the import and the split: 140-10_tables, 140-20_table_additions, 140-30_inserts, 150-10_procedures_functions, 150-20_views, 150-30_triggers, 150-40_events, 170_roles. **Routines before views**: `CREATE VIEW` on a function that does not exist yet fails (1305), a view on a missing view/table too (1146), while routine, trigger and event bodies are not checked at CREATE (verified on 12.3.2); 140 may regroup freely since Section 010 sets `FOREIGN_KEY_CHECKS=0`. `section_body(settings, development, section_id, parts, always_breakout, inline_before, inline_after)` builds a body and writes the breakout files (`breakout_text` = header + text, also used for the split's conflict check); `write_section_parts` is it plus one read-modify-write of the dev script. Each part is self-contained (its own DELIMITER block), so inline and breakout read the same. A breakout file is written only when its text changed (`write_if_changed`). The 160 writer in modeling still has its own rules (keeps an existing include and its slice); it shares `breakout_header`, `include_directive`, `set_section_body` and `write_if_changed`.
  - `modeling.create_project_from_workbench_model`: read model (or take `model=`, already read: the mcp tool reads it once for the folder name and hands it over), pick schema (several -> `schema` required), `lsp.require_lsp` BEFORE creating the folder, `create_schema_project_folder(allow_special_chars=True)`, write 140/150/170, then ONE load, `_replace_snapshot`, the diagrams appended (validated, reconciled against the snapshot, warning if anything dropped) and ONE `_write` of Section 160; on ANY failure the new folder is removed (`shutil.rmtree`). Checked against the MRS model: the 34 tables' columns, indexes and FKs match the project's Workbench-exported 140-10_tables.sql outline for outline except 3 columns the model changed after that export; both diagrams keep all figures/connections (30/36, 4/3).
  - **Splitting existing projects** (`msm.splitSections(schema_project_path, sections=None, lsp_path)` in `management.py`, mcp `msm.split_sections`; `modeling.split_sections` -> dict of `sections.split_sections`' `SplitResult(split, skipped, sections_added, files)` + `snapshot_updated`). Explicit only, never automatic (user's decision); 140/150/170 by default; always breakout files. First `complete_sections` adds every template section the script lacks (returns at once when the cached template ids are all there; rendered through `management.render_template_file` + `development_script_substitutions`, shared with project creation, with the 910 version; without 910 the last release + 1 patch, else 0.0.1), placed before the first higher-numbered id; only the added sections and the formerly last one get their trailing line breaks normalized, so a script with nothing missing keeps its hash. Then ONE `mariadb-lsp split` over the WHOLE dev script (sql_mode/DELIMITER context; offsets converted once by `statements.sql_entries`), every section planned before anything is written, the dev script written once; per section `statements.cut_section`, `statements.object_kind` per statement (TABLE = CREATE TABLE/SEQUENCE, TABLE_ADDITION = CREATE INDEX or an ALTER TABLE whose every clause adds a key, index or constraint (any other ALTER, a column or a rename, would change meaning when moved before the INSERTs, so it is unclassified), INSERT = INSERT/REPLACE, VIEW/PROCEDURE/FUNCTION/TRIGGER/EVENT for CREATE or DROP of one; 170 takes everything). Not `mysqlsh.mysql.split_script`: it drops DELIMITER lines and a `/* */` block between statements and detaches a trailing comment. Nor the splitter's `comment` entries: it merges neighbouring comments unpredictably; only the `sql` entries' offsets are used. Text rules: a statement takes the gap before it (the comments above it) and a line comment after it on its line; before the first statement only the run of line comments/blank lines right above it moves, so a `/* ToDo */` template example stays inline as the preamble; text after the last statement stays inline as the trailer; DELIMITER lines are dropped and `statements.render` re-wraps every run with a delimiter other than `;` in its own `DELIMITER` block; neighbours keep their original line breaks (`separator`). Statements of no part's kind before the first / after the last moved one stay inline before / after the directives. A section is LEFT ALONE and reported in `skipped` when it already has a SOURCE directive, has nothing to move, has an unclassifiable statement BETWEEN moved ones (user's decision), or a target breakout file exists with other content; so splitting twice changes nothing. `modeling.split_sections` remakes a schema snapshot that was `current` before (`update_schema_definition`) - its ranges and `source_hash` change with the move; a stale one is left stale so no diagram is reconciled implicitly.
  - `lib/statements.py` (no shell imports, used by workbench): `strip_statement` (leading `--`/`#`/`/* */` comments and DELIMITER lines off, a `/*!` versioned comment is code, the trailing delimiter off), `statement_kind`, `object_kind`, `char_offsets` (UTF-8 byte -> character offsets), `cut_section`, `render`.

## Gotchas / things not to repeat

- **A test sandbox can outlive its run**: if a suite's setup fails, the sandbox on 3388 keeps running after its temp dir is deleted, so `sandbox kill` cannot find it and the next run (msm or mrs) fails with `Port '3388' is already in use`. Check `ps` that the `--defaults-file` is under the pytest temp dir, then kill the pid.
- **Run the suite from the plugin dir** as `mariadb-shell --py -f run_tests.py` with `/opt/homebrew/bin` on PATH (`mariadbd`) and `MARIADB_SHELL` pointing at a shell that has `util.dump_schemas` (builds from 2026-10-01 on; `~/.local/bin/mariadb-shell` from Sep 29 lacks it). Never `pip install msm` — that is an unrelated PyPI package.
- **`run_tests.py -k` takes ONE word**: the runner pastes the pattern into the pytest command line split on spaces, so `-k "a or b"` fails with `file or directory not found: or`, and `a|b` selects nothing. Run one pattern per call.
- **`MARIADB_SHELL_USER_CONFIG_HOME` moves `plugin_data/msm_plugin`** (config, log, backups) — use a scratch one for experiments so the user's `workingDirectory` and update log are untouched.
- **Interactive mode changes return values**: wrappers print and return None when `useWizards` is on. Set `shell.options.useWizards = False` in scripts that need the values.
- **The `msm.set.sectionSqlContent` arguments are positional `file_path, section_id, sql_content`**; sections 140/170 (dev) and 240/270 (update) end up inside stored procedures — no `DELIMITER` there; 130/150/190/230/290 are top level and use `DELIMITER %%`.
- **Scripting the release functions** (used 2026-10-08 for the MRS metadata 5.0.0): from
  `mariadb-shell --py -f`, with a config home whose `plugins/msm_plugin` links to this repo
  (otherwise `ModuleNotFoundError: msm_plugin`), `useWizards` False, then
  `lib.management.set_development_version`, `prepare_release(version, next_version)`,
  `set_section_sql_content(section_id, sql_content, file_path)` on the update script and
  `generate_deployment_script(..., overwrite_existing=True)` to regenerate after an edit.
- **Section 240 runs INSIDE a stored procedure** (`msm_update_<from>_to_<to>`): a
  `DROP FUNCTION`/`PROCEDURE` there fails with MariaDB 1357 ("Can't drop or alter a
  FUNCTION from within another stored routine"); put such drops in 290. MariaDB also
  refuses to alter a column that is part of a FOREIGN KEY (1833): drop the FKs, alter,
  re-add them, all in 240.
- **The shell exposes plugin functions in snake_case in Python mode** (`msm.list_projects()`, `msm.add_project(...)`), camelCase is the registered FQN; the CLI form is `mariadb-shell -- msm list-projects` / `add-project <path> --folder=/Shop --color=green`. Verified 2026-11-04 through a scratch config home with `plugins/msm_plugin` linked to the repo.
- **CI runs on a case-sensitive Linux disk, the Mac on a case-insensitive one**: a test about case folding must branch on what the disk says (`os.path.exists` of the re-cased path) for every step, or it passes locally and fails in CI (an `add_project` of a re-cased path that does not exist there).
- **What a plugin function receives (checked with a probe plugin in a scratch config home):** from Python mode the shell's own `Dict` / `List` at every level, but they subclass `dict` / `list`, so `isinstance` and `json.dumps` work. This shell has no JavaScript mode. On the CLI a positional JSON object for a `dict` parameter is refused ("The following argument is invalid"); named options go into the dict parameter (documented keyword options go to `**kwargs`), each value parsed as JSON when it can be - also for a `str` option, which then fails with "String expected, but value is Map". Option names are camelCased, even `--x_y` -> `xY`. So a whole document comes in as a file (`msm set-schema-diagram --document-file=d.json`).
- **`MARIADB_SHELL_DISABLE_BUILTIN_PLUGINS=1` / `MARIADB_SHELL_PLUGINS_PATH` in the environment** (found set in the session's environment on 2026-11-06; added in mariadb-shell `1f0aa5cdc`) hide the shell's built-in plugins: no `sandbox` or `task` global, and the conftest fails with `cannot import name 'sandbox'`. Unset both for the suites.
- **msm finds `mariadb-lsp` next to the running shell before the PATH**: a stale copy in a shell build folder wins over a newer standalone lsp-server build on the PATH. To test with another binary, move the shell's copy aside for the run (and back), or pass `lsp_path`.
- **A docstring line ending in `:` is a section header to the shell's plugin parser**: "Invalid format: section without content", and the whole `msm` object fails to register (every msm test then dies with `No module named 'msm_plugin'`).
- **Legal notices are additive**: keep Oracle's line and the FOSS exception, add exactly `Copyright (c) 2026, MariaDB plc.`.
